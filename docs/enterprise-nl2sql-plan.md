# 企业级 NL2SQL 实施规划

> 版本：v0.2  
> 状态：方法论北极星 + **本仓库成绩域试点已落地（对应 Phase 0–4 的缩减切片）**  
> 原则：将 NL2SQL 建设为“可信数据查询能力”，而不是单纯的 SQL 生成器。  
> 关联文档：[`nl2sql-mvp-plan.md`](./nl2sql-mvp-plan.md)、[`nl2sql-eval-scores.v0.json`](./nl2sql-eval-scores.v0.json)、[`nl2sql-eval-scores.v0.results.json`](./nl2sql-eval-scores.v0.results.json)

## 1. 愿景与目标

面向已授权的企业用户，提供自然语言数据查询能力：用户可以用业务语言提问，系统依据统一的业务口径、数据权限与执行策略，生成并执行受控 SQL，返回可解释、可追溯的结果。

首期目标：在**一个业务数据域**中完成端到端试点，支持高频聚合分析问题，并满足以下要求：

- 仅允许读取受控数据视图，禁止任意 DDL/DML 与越权访问。
- 查询结果包含指标口径、数据范围、生成 SQL 或等价解释。
- 全链路可审计：请求、上下文、权限判定、SQL、执行结果摘要与策略拦截原因均可追踪。
- 通过真实业务问题集验证结果正确性、权限合规性、响应时延与成本。

### 1.1 本仓库已达成的试点目标（成绩域）

| 目标 | 落地情况 |
| --- | --- |
| 单域只读查询 | `student_base_info` + `ai0720score` 白名单；管理端 AI 助手 tool `query_data` |
| 权限范围 | 复用 `AccessContext.class_ids`：全校 / 老师班级列表 / 空列表拒答；学生门户关闭 |
| 可解释 | 返回 SQL、口径（不及格/及格/优秀）、数据范围说明；聊天侧表格 + 复制 SQL |
| 可审计 | `chat_nl2sql_logs` 记录 question / sql / class_ids / ok / refused / latency 等 |
| 可评测 | 25 题评测集；直播评测曾达 25/25；S01–S05、S15、S23 含结果等价 `expected` |

## 2. 首期范围与非目标

### 2.1 建议的首期范围（企业级）

- 一个口径成熟、业务价值高、数据负责人明确的数据域。
- 10–30 张受控查询视图、20–50 个核心指标和常用维度。
- 只读查询，优先支持筛选、分组、聚合、排序、时间比较与已定义指标。
- 有限试点用户群；查询前沿仅接入企业统一身份与权限体系。

### 2.2 本仓库首期范围（已落地缩减版）

| 项 | 本仓库选择 |
| --- | --- |
| 数据域 | **成绩**：`ai0720score` ⋈ `student_base_info` |
| 受控资产形态 | 白名单表 + 列白名单 + 强制软删注入（未建物理 VIEW，语义等价） |
| 接入面 | 管理端 Chat（`deepseek-chat` + tools）；门户账号 **不开放** NL2SQL |
| 身份权限 | 已有 JWT + RBAC；老师班级范围来自 `teacher_class` / `AccessContext` |
| 班级口语 | 「一班 / 1班 / AI0720-01」映射到 `class_info.id`（即学生表 `class_id`） |

### 2.3 首期非目标

- 不直接开放生产全库、原始明细表或敏感字段（如 `password_md5`）。
- 不将复杂跨域查询、自由明细导出和自动写入操作纳入 MVP。
- 不以“能生成可执行 SQL”为验收标准；必须验证结果和业务口径。
- **本仓库仍非目标**：就业域混查、完整语义平台/血缘、多租户网关、`deepseek-reasoner` 挂 NL2SQL。

## 3. 总体能力架构

```text
用户问题
  │
  ├─ 身份与权限上下文（租户 / 角色 / 数据范围）
  │
  ▼
意图识别与澄清 ──► 语义检索（指标、维度、同义词、数据目录）
  │                                      │
  ▼                                      ▼
受约束 SQL 生成 ◄────────── 受控 Schema / 查询视图裁剪
  │
  ▼
SQL 校验与策略引擎（AST、权限、敏感字段、成本、限流）
  │
  ▼
隔离执行环境 / 只读数据源
  │
  ▼
结果解释、SQL 展示、反馈收集、审计与监控
```

### 3.1 本仓库实际编排（成绩域实现）

```text
管理端 Chat 用户问题
  │
  ├─ set_nl2sql_context(enabled, class_ids, api_key, owner, conversation_id)
  │
  ▼
DeepSeek tool_calls → query_data(question[, sql])
  │
  ├─ 「我们班」多班澄清 / 单班自动补 class_id
  ├─ 班级名解析 + Schema 提示（classes.py / schema.py）
  ├─ 优先使用外层传入的 sql；否则 generate.py 二次生成
  │
  ▼
validate.py（sqlglot AST）
  · 单条 SELECT / WITH…SELECT
  · 表白名单、列白名单、禁 SELECT *、禁笛卡尔积
  · 强制软删 AND、老师 class_id IN (...)、LIMIT 封顶
  │
  ├─ 校验失败且为自动生成：回灌错误重试生成 1 次
  │
  ▼
execute.py（只读 Session，MAX_EXECUTION_TIME，fetchmany）
  │
  ▼
结果 JSON（rows/sql/metrics）→ tool 回填 → 模型组织自然语言回答
  │
  ├─ SSE: status「正在查询数据…」/ data_queries（表格+SQL+口径）
  ├─ chat_messages.data_queries_json 落库（刷新会话可还原）
  └─ chat_nl2sql_logs 审计
```

**代码落点：**

| 能力 | 路径 |
| --- | --- |
| Tool 注册与循环 | `backend/services/tools/registry.py` |
| query_data 入口 | `backend/services/tools/nl2sql/tool.py` |
| Schema / 口径 | `backend/services/tools/nl2sql/schema.py` |
| 生成 | `backend/services/tools/nl2sql/generate.py` |
| 校验 | `backend/services/tools/nl2sql/validate.py` |
| 执行 | `backend/services/tools/nl2sql/execute.py` |
| 班级解析 | `backend/services/tools/nl2sql/classes.py` |
| 权限上下文 | `backend/services/tools/nl2sql/context.py` |
| 等价比较 | `backend/services/tools/nl2sql/equiv.py` |
| Chat 编排 | `backend/api/v1/chat.py` |
| 直播评测脚本 | `scripts/nl2sql_eval_live.py` |

关键设计要点：

- **语义层优先**：业务指标、维度、口径、同义词、实体关系和可查询视图应有统一版本。  
  *本仓库现状*：口径固化在 `schema.METRICS` + 生成提示；尚未独立语义服务。
- **权限前置**：生成模型只接收当前用户被授权的数据资产与字段，不应依赖生成后再“补救式”过滤。  
  *本仓库现状*：生成提示带白名单 Schema；**执行前** AST 再强制注入老师 `class_id`（双重保险）。
- **多重校验**：生成后的 SQL 需经过语法、语义、权限、复杂度和成本校验，失败时安全拒答或引导澄清。  
  *本仓库现状*：语法/白名单/软删/班级/LIMIT/笛卡尔积；校验失败可重试 1 次；域外/写入倾向 `REFUSE:`。
- **人机协作**：展示口径与 SQL；支持用户修正、确认和反馈，为后续评测集扩充提供数据。  
  *本仓库现状*：聊天面板展示结果表、SQL、口径、复制 SQL；尚无人工改 SQL 再执行入口。

## 4. 分阶段计划

> 下列 Phase 为企业级节奏。每节末尾的 **「本仓库对照」** 标明缩减落地状态，便于对照阅读。

### Phase 0：立项与边界定义（企业 2–3 周 / 本仓库已完成）

**目标**：选择正确的首批场景，并明确可以安全上线的边界。

**主要工作**：

- 访谈业务、数据、安全与平台团队，选定 3–5 个高频分析场景。
- 确定目标用户、首期数据域、数据源、部署模式与合规要求。
- 盘点表、字段、数据质量、敏感分级、已有权限模型和现有指标体系。
- 定义基线指标：结果正确率、口径正确率、拒答合理率、P95 时延、单次成本、人工接管率。

**交付物**：场景清单与优先级、首期范围说明、数据资产清单、风险清单、成功指标定义。

**验收条件**：每个首期场景有业务负责人；每项数据资产有明确归属、敏感级别与访问策略。

**本仓库对照（完成）**：

- 选定成绩域；目标用户 = 管理端超管/主任/老师。
- 交付：`nl2sql-mvp-plan.md`、评测集 v0（25 题）、企业规划本文档。
- 基线门槛（MVP）：核心聚合等价率 ≥ 80%；越权 / 写操作 / 非白名单拦截 = 100%。

---

### Phase 1：数据治理与业务语义层（企业 4–8 周 / 本仓库完成缩减版）

**目标**：让业务语言能够稳定、可版本化地映射到受控数据资产。

**主要工作**：

- 建设指标、维度、时间口径、计算公式、同义词、实体关系和示例问法。
- 补齐表/字段描述、数据血缘、质量规则和数据新鲜度信息。
- 将可查询资产收敛为安全视图或语义模型，屏蔽原始表和不必要的高风险字段。
- 建立业务负责人审核、变更评审与版本发布/回滚机制。

**交付物**：语义层 MVP、受控视图清单、数据目录、口径说明、发布流程。

**验收条件**：核心指标和高频维度有唯一口径；首批问题可仅依赖受控资产完成查询。

**本仓库对照（缩减完成）**：

| 企业项 | 本仓库实现 |
| --- | --- |
| 受控视图 | 逻辑资产：活跃学生 / 活跃成绩 / 成绩⋈学生（白名单表 + 软删） |
| 指标口径 | 不及格 `score < 60`；及格 `>= 60`；优秀 `>= 90`；`exam_order` 1/2 |
| 字段治理 | `ALLOWED_COLUMNS`；禁 `password_md5`；禁裸 `SELECT *` |
| 同义词/口语 | 班级对照：`一班` ↔ `class_info.id` / `AI0720-0N` |
| 版本发布 | 代码内常量 + 提示词；尚无独立语义版本服务 |

**后续企业级缺口**：物理 VIEW、指标变更审批、血缘与新鲜度、跨域同义词库。

---

### Phase 2：安全执行与审计底座（企业 3–6 周 / 本仓库完成缩减版）

**目标**：使每条查询都受权限、成本和审计策略约束。

**主要工作**：

- 接入统一身份认证，落地 RBAC/ABAC、租户隔离和行列级访问控制。
- 使用 SQL AST 解析与策略校验：仅允许只读语句、白名单对象、受控函数与受限 JOIN。
- 限制扫描数据量、返回行数、并发、执行时间和单用户/单租户成本。
- 在只读副本、查询网关或隔离执行环境中执行；建立超时、熔断与降级机制。
- 留存审计记录与风险告警；敏感信息仅记录必要摘要并按合规要求脱敏。

**交付物**：权限适配层、SQL 策略引擎、执行网关、审计日志规范、告警规则。

**验收条件**：越权、写操作、非白名单对象和超预算查询可被拦截；审计记录覆盖所有试点查询。

**本仓库对照（缩减完成）**：

| 策略 | 行为 |
| --- | --- |
| 身份 | 管理端 JWT；门户关闭 NL2SQL |
| 行级 | 老师：`student_base_info.class_id IN (...)` 注入；空班级拒答 |
| 语句 | 仅 SELECT/WITH；禁多语句；禁 DML/DDL |
| 对象 | 表白名单 + 列白名单 |
| 成本 | 默认 LIMIT 200（最大 500）；`MAX_EXECUTION_TIME=5000`；禁 CROSS JOIN / 无 ON 多表 |
| 软删 | AST 强制 `is_delete=0` / `is_deleted=0` |
| 敏感列 | 校验拦截 + 执行结果抹除 |
| 审计 | `chat_nl2sql_logs`（question、sql、class_ids、ok、refused、generated、retried、row_count、latency_ms、error） |

**后续企业级缺口**：独立只读副本/查询网关、租户级配额与告警平台、列级 ABAC 细粒度、审计合规脱敏规范。

---

### Phase 3：受控单域 NL2SQL MVP（企业 4–6 周 / 本仓库完成）

**目标**：在一个数据域内形成可用、可解释的查询闭环。

**主要工作**：

- 构建“意图识别 → 语义检索 → Schema 裁剪 → SQL 生成”的编排链路。
- 实现生成后校验、执行错误修复、歧义澄清与无法安全回答时的拒答策略。
- 返回结果时同步展示数据范围、指标口径、过滤条件与 SQL/等价解释。
- 提供 SQL 查看、人工编辑/确认和结果反馈入口。

**交付物**：MVP 服务、前端/接口集成、提示词与检索策略版本、反馈闭环。

**验收条件**：在离线核心问题集上达到项目定义的最低结果等价率和口径正确率；所有查询经过权限与策略校验。

**本仓库对照（完成）**：

1. **编排**：Chat tool loop → `query_data`；可选外层直接给 `sql`（降二次 LLM 成本），否则 `generate_sql`。
2. **修复**：校验失败回灌 `previous_sql + validation_error`，再生成 1 次。
3. **澄清 / 拒答**：
   - 「我们班」+ 多班 / 全校 → 要求明确班级；
   - 就业/薪资、删改、sys_user 等 → `REFUSE:` 或策略拦截。
4. **前端（管理端 / 门户 UI 对齐，门户权限仍关闭）**：
   - SSE `status`：正在查询数据…  
   - `data_queries`：结果表、SQL、口径、复制 SQL；  
   - `data_queries_json` 随 assistant 消息落库。
5. **依赖**：`sqlglot`（`backend/requirements.txt`）。

**后续企业级缺口**：独立意图分类服务、向量语义检索、用户改 SQL 确认后再执行、结果反馈工单。

**目标**：用真实业务问题验证可信度，识别可控边界外的风险。

**主要工作**：

- 建设问题集：自然语言问题、授权上下文、标准 SQL/结果、口径说明、难度和风险标签。

- 以灰度方式对业务试点开放，依据错误分类优化语义层、检索、提示、策略和数据质量。

**交付物**：评测集与自动化评测流水线、红队报告、试点运营报告、缺陷闭环清单。

**验收条件**：达到预设上线阈值；高风险问题均有拦截/拒答/人工接管路径；试点业务负责人确认核心场景可用。

## 5. 评测与上线指标

建议将问题按简单聚合、时间比较、多表关联、口径歧义、权限敏感和不可回答等类别分层；每次版本发布都运行固定基准集。

- **结果质量**：执行成功率、结果等价率、指标口径正确率、筛选条件正确率。
- **安全合规**：越权拦截率、敏感字段泄漏次数（目标为 0）、审计覆盖率。
- **体验**：P50/P95 响应时延、澄清率、拒答合理率、人工接管率、试点用户满意度。
- **效率与成本**：单查询模型和计算成本、扫描数据量、缓存命中率、超时率。

上线阈值应由业务、安全和平台共同确定；不要以单一“SQL 生成成功率”代替结果正确性与安全性验收。

### 5.1 本仓库当前阈值与跑法

| 指标 | 建议阈值 | 本仓库状态 |
| --- | --- | --- |
| 核心聚合结果等价 | ≥ 80% | S01–S05/S15/S23 有 expected；其余题以可执行+策略为主 |
| 越权 / 写 / 非白名单拦截 | = 100% | 策略单测 + 直播拒答题 |
| 审计覆盖试点查询 | = 100% | `chat_nl2sql_logs` |
| 敏感字段泄漏 | = 0 | 列白名单 + 执行抹除 |

**本地跑评测：**

```powershell
$env:PYTHONPATH="backend"
```

## 7. 主要风险与应对

| 风险 | 应对策略 |
| --- | --- |
| 指标口径不一致 | 先治理语义层；指定指标负责人；变更可审计、可回滚。*本仓库：口径写死在 schema/提示，变更需发版。* |
| 模型幻觉或错误 JOIN | 仅提供裁剪后的受控资产；使用 AST/语义/执行多重校验。*本仓库：白名单+软删注入+失败重试。* |
| 数据越权与泄露 | 权限前置、行列级控制、查询隔离、脱敏审计和红队测试。*本仓库：class_ids 注入 + 敏感列拦截 + 门户关闭。* |
| 大查询拖垮仓库或成本失控 | 扫描量与时延预算、限流、缓存、只读副本和熔断。*本仓库：LIMIT + 语句超时 + 禁笛卡尔积。* |
| 用户过度信任结果 | 显示口径、范围和 SQL；突出不确定性；保留人工确认入口。*本仓库：已展示 SQL/口径/表格；尚无确认后再执行。* |
| 扩域后质量下降 | 以数据域为单位接入和发布；每域有独立评测集与负责人。*本仓库：下一域建议复制成绩域模板。* |
| 双次 LLM 成本偏高 | *本仓库：优先让 Chat 外层直接传 `sql`；仅不确定时二次生成。* |
